# نشر RePayControl وتشغيله

## بيئة التشغيل

خادم Node.js 24، وقرص دائم لقاعدة SQLite، وHTTPS أمام الخادم. لا توجد تبعيات npm خارجية. يفتح التطبيق افتراضيًا المنفذ 4317. لا تشغّل عدة نسخ فوق أقراص منفصلة؛ هذا الإصدار يستخدم قاعدة واحدة على خادم واحد.

ملف `.env.example` يحصر المتغيرات المطلوبة. الإعداد المحلي:

```sh
node src/setup.mjs
npm start
```

للإنتاج يمكن إنشاء الأسرار في مدير أسرار الاستضافة، كل واحد بقيمة عشوائية مستقلة. لا تستخدم قيم المعاينة أو كلمة مرور قصيرة. لا تُطبع الأسرار في السجلات. يفشل تشغيل الإنتاج مبكرًا إذا لم تكتمل الأسرار الثلاثة أو كانت قصيرة.

## Docker

انسخ `.env.example` إلى `.env` وأكمل أسراره محليًا، ثم اضبط `NODE_ENV=production`.

```sh
docker compose up -d --build
```

يحفظ Compose البيانات في volume باسم `control-data`. منفذ المضيف مربوط بـ127.0.0.1؛ ضع HTTPS reverse proxy أمامه. مثال Nginx بعد إعداد الشهادة على النطاق:

```nginx
location / {
    proxy_pass http://127.0.0.1:4317;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 64k;
}
```

استخدم النطاق المختار الفعلي في إعداد الاستضافة. جلسة الإنتاج تستعمل Cookie بـSecure وHttpOnly وSameSite=Strict؛ لن تعمل على HTTP عادي. استثنِ مسارات `/api/events` و`/api/server-events` من أي بوابة تسجيل دخول خارجية تعوق استقبال القياس؛ حماية البيانات الإدارية موجودة على الخادم. مسار الخادم يتطلب Bearer خاصًا لا يُرسل من المتصفح.

## الصلاحيات ومصادر البيانات

- بيانات اللوحة وCSV وجميع المصادر تتطلب جلسة الإدارة.
- `/api/events`: قياس متصفح غير موثوق، بموافقة المستخدم، مع CORS على نطاقات محددة وربط النطاق بالمشروع. هذا **ليس إثبات هوية**؛ يمكن لأي عميل غير متصفح تزوير Origin. لا تستخدمه لإثبات دفعات أو مستخدمين مسجّلين.
- `/api/server-events`: أحداث تجارية تتطلب مفتاحًا خاصًا. هذا الإصدار يستخدم مفتاح خادم مشتركًا للمشاريع الموثوقة؛ تدويره يستلزم تحديثها جميعًا. لمستويات عزل أعلى أضف مفاتيح مستقلة لكل مصدر.
- الحد الداخلي افتراضيًا 240 دفعة متصفح/دقيقة لكل عنوان اتصال، و600 دفعة خادم/دقيقة، و5 محاولات دخول/15 دقيقة. التطبيق لا يثق في X-Forwarded-For. خلف reverse proxy قد تشترك الاتصالات في الحد؛ ضع حدودًا حسب العميل على الحافة واضبط القيم الداخلية عند زيادة الاستخدام.
- لا تخزن SQLite عنوان IP. محدد المعدل يحتفظ بعنوان اتصال الشبكة في الذاكرة فقط. اضبط أيضًا سياسة سجلات الاستضافة والبروكسي؛ فهي مستقلة عن قاعدة القياس.

## اختبار بعد الربط

1. افتح `/health` وتحقق من `{"status":"ok"}`، ثم افتح اللوحة وسجل الدخول.
2. ثبّت الربط في نسخة من كل مشروع واضبط نطاقات CORS وCSP الفعلية.
3. قبل قبول القياس: تحقق من عدم إرسال طلبات `/api/events`.
4. اقبل القياس، وافتح صفحة واضغط زرًا، ثم حدّث اللوحة: يجب أن تظهر مشاهدة ونقرة للمنتج الصحيح.
5. أرسل نموذج الأعمال اختباريًا مرة واحدة فقط ببيانات تملكها. تأكد من وجود الصف في Google Sheets ثم حدث `lead_created` بالجلسة نفسها. لا تستخدم الإنتاج لاختبارات وهمية جماعية.
6. جرّب إعادة إرسال دفعة واحدة بنفس event IDs؛ يجب ألا تتضاعف الأعداد.
7. افتح صفحة نجاح المحفظة دون دفع: يجب أن يبقى عداد الدفعات المؤكدة دون زيادة.
8. للدفعات الفعلية: ضع الحدث داخل مسار تحقق webhook المزوّد، ومرر معرف حدث مستقرًا و`currency: SAR` والمبلغ بالهللات بعد تحقق التوقيع والنتيجة. لا تضف الحدث إلى زر الدفع.
9. صِل POC وGoogle Sheets وتحقق من حالة «متصل». بياناتهما التاريخية مستقلة عن فلاتر الفترة والمشروع، ويبيّن العرض ذلك.
10. اسحب موافقة القياس من «تفضيلات القياس»، وتحقق من توقف إرسال الزيارات والنقرات.

## الاحتفاظ والنسخ الاحتياطي

الحذف التلقائي حسب `RETENTION_DAYS` (افتراضيًا 90، والحد الأقصى 365) عند بدء الخادم ثم كل ساعة. جداول الفترات تعرض حتى 90 يومًا. تغيير مدة الاحتفاظ لا يستعيد ما حُذف. خذ نسخة متسقة باستخدام SQLite backup API أو أوقف الخدمة أثناء نسخ مجلد البيانات بما فيه WAL، واختبر الاسترجاع. لا تُنسخ ملفات SQLite الساخنة منفردة مع تجاهل WAL.

تدوير `SESSION_SECRET` يبطل جلسات الإدارة ويغيّر تجزئة المستخدمين للأحداث الجديدة؛ ضع ذلك في الحسبان عند مقارنة الهويات. تدوير مفاتيح استضافة المصادر مستقل عن مفاتيح RePayControl.
